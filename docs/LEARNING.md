## T03：截止规则与提醒状态

**核心技术：** 时间比较、优先级排序、提醒阶段、避免重复处理。

**掌握的问题：** 为什么“紧急排序”和“触发提醒”需要两套判断？为什么每次检查不能都弹窗？

**证据边界：** 完整 10 分钟推迟与到期后的逾期面板已观察到；观察时间不等于精确触发时间，也不等于系统横幅送达时间。

## T04：Windows 快捷入口与单实例

**实现状态：** 已实现；真实登录自启与注销待验收。**学习状态：** 待用户解释。

**核心技术：** Windows 全局热键、资源释放、单实例锁、本地进程通信、可选登录自启。

**掌握的问题：** 为什么重复启动应该唤醒已有窗口，而不是再运行一个提醒进程？

**参考理解：** 同一数据库只保留一个运行实例，可以减少重复提醒与热键争用。新进程通过本地通信请求已有实例显示窗口，收到确认后退出。锁只能限制实例数量，不能证明持锁进程仍健康。

**观察入口：** [desktop.py](../src/focuspilot/desktop.py) 的 `InstanceGuard`；[windows.py](../src/focuspilot/windows.py) 的热键和自启适配器。小练习：解释隐藏窗口时保留热键、退出时释放热键的原因。

**证据边界：** 快捷键、冲突提示、重复启动与正常退出后释放已实测；自启默认关闭。旧正式实例曾持锁但唤醒不响应，经用户授权结束并重启，根因尚未定位。不能把锁恢复或重启成功当作根因修复。

## T05：可配置提醒系统（当前学习重点）

**实现状态：** 已实现并完成隔离 GUI 验证。**学习状态：** 理解与验证练习进行中，尚未完成用户学习验收。

### 功能与默认决策

- 普通提醒支持仅面板、标准、强提醒三种方式。
- 可选每日工作时段，支持跨午夜；可设置一次性免打扰。
- 用户已明确选择“逾期任务仍强提醒”，默认开启，可关闭；仍尊重任务推迟和全局通知间隔。
- 通知间隔为 1–60 分钟，默认 1 分钟；同轮主动提醒合并执行。
- 设置、提醒阶段与最近通知时间保存在 SQLite，重启保留。
- 强提醒表示提醒动作更明显，不表示不断响铃。没有调用模型，也没有发送任务数据到云端。

### 五个知识点：先理解原因，再看实现

| 知识点 | 为什么需要 | 本项目如何实现 |
| --- | --- | --- |
| 1. 定时检查与确定性 Workflow | 截止时间不能依赖模型延迟、费用或推理是否稳定 | Qt 的 QTimer 约每 30 秒调用 `tick`，使用当前时间计算；不是硬实时调度，阻塞或睡眠会影响执行时刻 |
| 2. 状态管理与避免重复提醒 | 每次轮询都满足“已逾期”时，不能每次都通知 | `reminder_to_send` 检查任务状态、推迟时间与已处理阶段；抑制的阶段保留，恢复后按当前阶段处理 |
| 3. 策略与执行分离 | 产品规则需要独立理解和测试，不应散落在弹窗代码里 | `delivery_policy` 返回是否允许、横幅、恢复面板、声音；`tick` 执行动作。逾期例外优先于免打扰，推迟和通知间隔仍有效 |
| 4. 持久化与事务 | 重启不应遗忘配置或清空冷却；部分保存会造成状态矛盾 | `record_reminders` 在同一 SQLite 事务保存阶段与通知时间；提交失败不通知，下轮重试 |
| 5. 测试证据与交付边界 | 规则正确、接口被调用和用户收到提醒是不同层次 | 自动测试校验规则与失败路径，真实窗口校验交互，系统横幅和声音仍需实际确认 |

本阶段最重要的三个知识点：**确定性调度、显式状态与持久化、分层验证**。策略分离让这些规则更容易理解和测试。

### 核心代码与执行链路

| 文件 | 职责 | 建议观察的入口 |
| --- | --- | --- |
| [core.py](../src/focuspilot/core.py) | 根据任务状态识别待处理提醒阶段 | `reminder_to_send` |
| [reminders.py](../src/focuspilot/reminders.py) | 配置校验、工作时段、免打扰、提醒强度、通知间隔 | `ReminderSettings`、`delivery_policy`、`cooldown_remaining` |
| [storage.py](../src/focuspilot/storage.py) | 保存设置、提醒阶段和通知时间 | `save_reminder_settings`、`record_reminders` |
| [gui.py](../src/focuspilot/gui.py) | 设置表单、定时检查、面板与通知执行 | `ReminderSettingsDialog`、`tick`、`refresh` |

```text
QTimer 唤醒
  → 读取任务
  → 排除完成、无 DDL、仍在推迟期间及已处理阶段
  → 判断 soon / overdue
  → 应用提醒策略和全局通知间隔
  → 同事务保存本轮阶段及通知时间
  → 合并执行横幅 / 恢复面板 / 提示音
  → 刷新显示；用户完成或推迟后进入下一轮
```

注意：本地数据库与 Windows 通知系统之间没有共同事务。先记库、后通知能避免一部分重复，但若提交后、通知前崩溃，可能漏掉该次提醒；目前没有送达确认机制，不能声称“恰好送达一次”。

### 理解设计：需要掌握的问题

**为什么提醒必须独立于 Agent 运行？**

参考理解（来自用户给出的示例，尚不作为学习验收结果）：

> 因为定时提醒属于确定性任务。如果完全依赖大模型，就可能出现调用延迟、成本增加以及执行不稳定的问题，因此应由本地调度器负责，Agent 只参与需要智能判断的任务。

**Workflow 与未来 Agent 的分工：** 当前时间计算、状态变更、通知和持久化由本地代码完成；未来 Agent 可以提出拆解和计划建议，工具权限与写入校验仍由应用执行。T05 当前全部属于 Workflow。

### 解释原理：三个学习验收问题

1. **架构：** 如果未来 Pi 断网或模型调用卡住，为什么提醒应该继续工作？你会把时间判断、任务保存、智能规划分别放在哪一层？
2. **实现机制：** 一项任务在免打扰期间从临近截止变成逾期，且逾期例外关闭。免打扰结束后，应该补发哪些提醒？需要保存哪些状态，才能在重启后继续正确处理？
3. **产品设计：** 为什么选择“逾期仍强提醒”，却又让它尊重手动推迟和通知间隔？如果测试全部通过，但用户没看到 Windows 横幅，你会怎样继续验证？
