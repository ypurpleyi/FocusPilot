# T07：Pi进程内MCP适配器评审

状态：2026-10-24，用户选择A2后实现；真实Pi进程内MCP固定调用、工具集合及取消/超时清理已通过，模型/生产GUI仍待接入。下文“获选后/待选择”为设计历史。

## 为什么调整

宿主MCP桥接的固定客户端实测已通过，但本机Node v24.15.0/libuv1.51.0在AppContainer内创建stdio子进程卡住，真实Pi未能启动转发代理。不能关闭沙箱继续运行，也不能把固定客户端成功当作Pi接入成功。

## 推荐：Pi进程内适配，仍使用MCP协议

```text
FocusPilot ── RPC控制 ──> AppContainer内的Pi
                         └─ 专属扩展注册两个工具
                             └─ MCP客户端 + 自定义管道Transport
                                 └─ 专属Windows管道
                                     └─ 宿主Broker身份/预算检查
                                         └─ Python MCP服务
                                             └─ 只读虚构SQLite
```

| 组件 | 本阶段职责 |
| --- | --- |
| Extension（扩展） | 把两个只读能力绑定到Pi工具系统；不是通用扩展加载入口 |
| Adapter（适配器） | 将Pi工具参数/结果与MCP调用格式对应起来 |
| Transport（传输实现） | 实现MCP客户端的start/send/close及消息、错误、关闭事件，通过专属命名管道传JSONL |
| Broker（权限代理） | 复用宿主SID、零能力、Job、协议、参数、预算检查；扩展不能自行授权 |

这不是在mcp.json里填一个管道URL。已安装的`@earendil-works/pi-mcp`1.4.0公开`McpClient.connect(McpTransport)`接口；Pi公开`registerTool`、`session_start`、`session_shutdown`。使用这些公开接口，不改原Pi/Node安装代码、不依赖未导出的bundle内部类。

Pi会看到扩展注册的工具；MCP客户端仍要真实执行initialize、tools/list和tools/call。不能把这一路径记为Pi内置stdio MCP管理器已修复，也不要求`pi mcp list`展示该自定义适配器。

## 两个可选方案

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| A2，推荐：进程内MCP适配扩展 | 复用当前运行时、已验证宿主桥接和只读工具，避开代理子进程 | 维护自定义Transport、工具绑定及生命周期；必须单独测试 |
| B：暂保留原生stdio设计 | 继续使用Pi内置MCP管理方式 | 等待并确认兼容的官方运行时，再单独评审/验证；当前接入保持未完成 |

## A2获选后的一个实现阶段

1. 先写离线测试，再实现有界JSONL管道Transport；复用已安装MCP客户端，不下载依赖。限制大小、队列、绝对时限；断线/重复响应/非法消息失败即关闭，send遵守取消信号，不在取消后重新派发。
2. 编写一份随项目维护的专用扩展。运行时只显式加载该扩展；关闭全局/项目扩展自动发现、内置MCP配置发现和无关默认工具。使用本轮独立配置，无原始凭据。
3. MCP初始化/发现后核对名称及输入输出Schema与固定的list_tasks、find_duplicate_tasks契约；拒绝额外工具/Schema不符。Pi仅激活这两个工具；工具回调只能调用对应MCP方法，无路径、SQL或脚本参数。
4. session_start建立连接，session_shutdown幂等关闭。工具回调收到取消或连接失败时返回失败，不能伪造空查询；应用与宿主仍负责本轮失效及Job回收。扩展错误使本轮不可用，不普通权限回退或自动收费重试。
5. 在新的专属临时AppContainer与只读程序副本内验证真实Pi加载、工具注册和MCP固定调用。沿用已授权的虚构库方式，只复制程序与本轮适配代码；不改源ACL、全局配置或系统设置。

扩展与Pi在同一沙箱身份下，并非新增独立安全边界；扩展运行不应得到数据库文件或额外网络权限。宿主Python服务仍属于TCB（可信计算基），不能因此声称它被OS全面禁止写入。

## 验收门槛

- 单元层：分片/超限/无效JSON、请求关联、重复响应、取消前后派发、断线、幂等关闭及Schema不匹配。
- 固定集成层：真实MCP握手/发现/调用，待办与重复候选各2项、ID精确匹配、未截断；服务端转发记录与客户端结果对应。
- 真实Pi层：确认专属扩展被加载，Pi工具目录/激活集合仅包含两个预期工具；固定离线驱动执行与注册回调共用的调用路径。不是模型自主选工具，不称为Agent Loop验收。
- 权限层：仍核验AppContainer SID、零能力、Job；不能直接读库；非法工具/参数及错误身份不进入查询。
- 生命周期层：取消/超时/初始化失败停止，迟到结果无效；宿主与容器自建进程、线程、管道、profile、副本清理，虚构库哈希不变。

不读取凭据、正式待办或任意私人目录；不调用模型、不开放网络、不安装或升级运行时、不新增GUI、不推进T08、不提交推送Git。如果Pi加载器或公开接口在当前沙箱仍不兼容，保留失败证据并停止，不修改权限边界兜底。

## 接口核对依据

本机安装包`docs/extensions.md`的MCP servers/Tools/资源生命周期章节；`dist/core/extensions/types.d.ts`的ToolDefinition与ExtensionAPI；随包`@earendil-works/pi-mcp/dist/client.d.ts`和`dist/transports/transport.d.ts`。这是静态接口核对，尚不是运行兼容证据。

## 实际结果

`mcp_transport.mjs`实现有界JSONL、响应关联、绝对时限和幂等关闭；关闭时主动拒绝尚未回调的写入，避免取消后挂起。`mcp_adapter.mjs`核验工具名称/Schema、参数、结构化与文本结果一致性及运行代次。`pi_mcp_extension.mjs`为离线专用扩展，固定驱动调用它向Pi注册的同一回调；没有模型自主选择工具。

`pi_inprocess_probe.py`复用专属副本和宿主桥接，在真实AppContainer中运行Pi1.4.0。最初`--no-tools`令Pi工具目录为空，虽回调查询成功仍被证据检查拒绝；改为`--no-builtin-tools --tools`加两个精确工具名，同时关闭内置MCP和自动扩展/技能/上下文发现。实际目录/激活集合恰有两个工具。

正常查询得到两项待办与两项重复候选，精确ID一致且未截断；模拟取消与截止时间到期后，扩展撤销激活并拒绝后续调用。三轮均正常结束RPC，shutdown执行、激活集合清空；容器/宿主Job、读写线程、管道均清理，profile、副本、工作区删除，库哈希及原安装关键指纹/ACL未变。见[脱敏结果](T07_PI_INPROCESS_VALIDATION.json)。

一轮超时场景在连接阶段失败、未进入查询，原因尚未确定；固定错误码/通道标识诊断加入后，独立重跑三场景通过。不能将重跑成功当作已证明长期稳定，生产仍需可见失败与取消，不自动放宽权限重试。另有一次工具自动审批超时，按工具允许只重试一次后执行，没有安全性拒绝或扩大授权。

原生stdio子进程问题未修复；本轮无模型、凭据、正式任务、网络或GUI。下一步进入应用可用链路，保留工具与数据边界。
