## 阶段结论：截至 T05，搭建的是本地 Workflow 基础闭环

**这一判断成立。** 当前由明确规则和事件驱动，完成“记录—保存—检查—提醒—反馈”的流程；没有接入 Pi、模型推理、Tool Calling 或 Agent Loop。

这里的 Workflow 是写在应用代码中的流程，不要求使用可视化工作流平台。“基础闭环已搭建”不等于所有功能和系统场景都已验收：任务编辑/删除、真实登录自启与注销、系统通知送达仍有待办。

设计原则：**数据库保存事实，规则判断状态，策略决定打扰方式，界面执行动作。** 未来 Agent 提出智能建议，应用负责权限校验和可靠执行。

## 系统链路

```text
点击添加任务 / Ctrl+Alt+N
  → 校验输入 → SQLite 保存
  → 面板读取、排序和显示
  → QTimer 约每 30 秒检查
  → 排除已完成、无 DDL、仍在推迟期间及已处理阶段
  → 判断临近截止 / 已逾期
  → 应用提醒强度、工作时段、免打扰和通知间隔
  → 同事务保存本轮提醒阶段与通知时间
  → 合并执行横幅 / 恢复面板 / 提示音
  → 用户完成或推迟 → 保存状态 → 下一轮检查
```

排序决定“先看什么”，提醒决定“何时打扰”。程序退出、电脑关机或睡眠时不能继续按时检查；这不是硬实时系统。

## T07：核心知识与离线实现（真实Pi未接入）

| 术语 | 对应关系 | FocusPilot 例子 |
| --- | --- | --- |
| API：应用程序接口 | 定义能力入口，不限于网络接口 | 查询候选重复任务 |
| Interface Contract：接口契约 | 约定输入、输出、错误和行为边界 | 接收草稿，返回候选重复项，只读正式任务库 |
| Schema：数据结构规范 | 描述字段、类型和必填项 | 标题为字符串，截止时间可空，耗时为整数 |
| Tool Calling：工具调用 | 模型提出工具名和参数，程序校验、执行并返回结果 | 请求准备任务草稿并查重 |
| RPC：远程过程调用 | 跨进程或机器调用；Pi RPC 是具体协议 | Python 后台控制 Pi 子进程；不是 MCP 的同义词 |
| MCP：模型上下文协议 | 标准化 AI 应用连接工具与数据源 | 已选用并实现本地只读服务；尚未连接真实Pi/模型 |
| Adapter：适配器 | 将调用方式转换为业务接口调用 | Pi 自定义工具或 MCP 适配同一查重能力 |
| Decoupling：解耦 | 调用方依赖稳定契约，减少对内部实现的依赖 | 数据库表变化时，业务工具契约可以保持稳定 |
| Agent Loop：智能体执行循环 | 模型判断、工具执行、结果回到上下文，按需要继续 | 提取任务 → 准备草稿工具 → 校验结果 → 修订或回复 |

记忆关系：**API 定义入口，Contract 约定规则，Schema 描述数据，Tool Calling 是调用行为，MCP 标准化工具连接。** Schema 校验与 MCP 本身均不能替代权限控制。

已明确的产品目标：文本可含多任务；先确认数量和清单，再检查字段；缺失截止时间由用户补充，重要程度/耗时允许标注建议或估计；Agent 可读正式任务，不能修改。数据库查重返回候选项，由用户决定丢弃新草稿或仍然新增。

用户已确认的首版查重决策：仅匹配未完成任务中的同名候选；日期不同展示差异，已完成任务默认不参与，不做语义近似匹配。学习重点：**Candidate Match（候选匹配）不等于事实判定；Acceptance Criteria（验收条件）要用明确的输入与预期结果描述。** 规则已确认不代表代码已实现或测试已通过。

Schema 设计练习（草案，未实现）：草稿保存字段值和来源，`null` 表示尚无确定值；建议/估计不能标为原文事实。**Schema Validation** 检查结构，**Business Validation** 检查规则，**Human Review** 检查语义。批次 ID、实际数量、查重结果与确认状态由应用掌握（Authority），模型不能自行声明。学习问题：为什么“耗时为整数 30”结构合法，却仍需标注估计并让用户检查？

**我的理解（用户原话）：** 针对“明天下午”被填为 17:00 的问题：“需要人工检查，必须由用户来确定进入sql的内容。这里要明确工具和agent的权限边界”。

导师补充：17:00 是原文未给出的精度，应标记含糊、留空并请用户补充，不仅依赖用户发现猜测。用户确认的是任务字段，不是模型生成的 SQL；Agent 提议、工具只读查重并准备草稿、界面记录当前版本确认，最终由应用校验并使用参数化 SQL 保存。确认不能绕过合法性检查，也不能由模型声称。这记录了本题的理解，不代表整个 T07 学习或集成已验收。

RPC 生命周期设计（草案，未实现）：**Acknowledgement（接受确认）≠ Completion（执行结束）≠ Business Success（业务成功）≠ Persistence（保存成功）**。prompt 成功不等于模型完成，agent_settled 表示自动处理收敛，仍需检查最终错误和有效工具草稿；保存成功以数据库提交为准。**Correlation ID（关联标识）** 关联命令响应，本地 run_id/进程代次隔离旧结果；取消后迟到消息不得影响新表单。**Timeout/Cancellation（超时/取消）** 要使本地运行失效，不能只隐藏加载动画。后台处理保证 T05 提醒独立运行；待实现和验证。

**我的理解（用户原话）：** 针对取消后迟到完成事件是否应打开确认界面：“不应该，用户的取消是新的需求提出，此时应该有一个子功能来处理这类紧急事务然后返回取消之后的原始界面”。

导师补充：取消属于应用的 **Control Signal（控制信号）**，由确定性取消处理器响应，不作为新提示词等待模型处理。先使运行/草稿失效，返回保留原文的输入界面，再后台请求停止并清理；迟到事件不得开表单或写库。界面返回不等于后台已停止，清理完成前不复用旧进程。该回答说明用户已理解“取消优先且不能打开确认界面”，实现机制尚待验证。

离线验证：用 **Test Double（测试替身）** 中的 Fake Pi 产生可控事件，以 **Assertion（断言）** 验证行为，以 **Invariant（不变量）** 定义始终成立的边界，例如取消后不发布旧结果、不自动写库。已新增45条测试；模拟验证接入控制，不证明模型理解准确或真实Pi兼容，T08草稿场景未执行；详情见 [离线模拟测试计划](../PI_HARNESS_TEST_PLAN.md)。
