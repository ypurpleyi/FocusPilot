## 目标与分期

用户粘贴通知或输入文本 → 分析多项任务 → 查询候选重复 → 确认数量与清单 → 检查字段 → 用户保存正式任务。

- T07：后台 RPC、受限只读能力、运行状态和失败降级。
- T08：自然语言草稿、多任务确认、字段补全和确认后保存。
- 当前先设计接口，不同时启动两个 Ticket 的开发。MCP 是可选适配方案，不是接入前提。

## 用户已明确的规则

1. 分析完成后，先显示识别数量和任务清单，经用户确认后进入字段确认界面。
2. 截止时间缺失时提示用户补充，不擅自生成；仍可由用户明确选择无截止时间。
3. 重要程度与耗时允许建议值，但必须标注，由用户检查。
4. Agent 可以读取正式任务，不得修改正式任务数据库。
5. 候选重复须显示对应任务，用户可丢弃该项新草稿或选择仍然新增；不自动合并、删除旧任务。
6. 首版只检查未完成任务中的同名候选；同名同截止时间提示可能重复，同名不同截止时间展示日期差异，已完成任务默认不参与。首版不做语义近似匹配。此规则已由用户确认。

## 查重规则与验收示例（只读匹配已实现，确认交互待T08）

以下使用虚构任务，不访问正式数据库。规则由确定性代码执行，模型不自行扩大查询范围。标题匹配首版建议仅去除首尾空白后精确比较，不把“含义相似”当成同名。

| 已有任务 | 新草稿 | 预期结果 |
| --- | --- | --- |
| 未完成，“提交周报”，本周五截止 | 同名，同一截止时间 | 返回候选，用户选择丢弃新草稿或仍然新增 |
| 未完成，“提交周报”，本周五截止 | 同名，下周五截止 | 返回候选并展示日期差异；不自动认定重复 |
| 已完成，“提交周报” | 同名 | 不作为正式任务库的首版查重候选 |
| 未完成，“提交周报” | “整理每周汇报” | 不因语义相近而匹配；说明首版覆盖范围 |
| 未完成，“提交周报”，无截止时间 | 同名，无截止时间 | 返回候选；缺失日期不能证明相同或不同 |
| 读取数据库失败 | 任意草稿 | 显示查重失败，不能声称没有重复；保留输入和草稿 |

同批草稿的相同项也应作为待确认提示，不静默丢弃；具体同批提示交互在 T08 完善。查询失败时推荐暂停自动草稿确认入口，提供重试或转手动录入，不影响现有提醒。

计数示例：原文识别 3 项，其中 1 项有候选重复 → 显示“识别到 3 项任务，其中 1 项可能重复” → 用户丢弃这份新草稿后显示“保留 2 项待确认”。“丢弃”不删除库内旧任务。

## 推荐的最小工具契约（待评审）

首版向模型暴露一个 `prepare_task_drafts` 工具；应用内部组合字段校验、查重和内存草稿管理。这样每份进入确认流程的草稿都经过检查，不依赖模型主动记得调用另一个查重工具。

| 项目 | 契约草案 |
| --- | --- |
| 工具输入 | `tasks[]`；每项含标题、可空截止时间、重要程度、预计耗时、字段来源与原文依据 |
| 应用提供的上下文 | 本次请求标识、输入文本、参考时间、允许的数据范围；不能由模型自行扩大 |
| 工具输出 | `batch_id`、`revision`、有效草稿及数量、候选重复项及依据、缺失字段和错误 |
| 读取边界 | 仅读取查重所需任务字段；不接收 SQL、数据库路径或任意文件路径 |
| 状态边界 | 可以暂存本次会话的内存草稿，不写入正式任务库；这与禁止 Agent 修改正式任务不冲突 |
| 错误 | 字段无效、数据库读取失败、请求取消、会话过期；读取失败不得伪装为没有重复 |

`find_duplicate_tasks` 是工具内部的只读业务接口。未来确有独立查询需求时，再考虑单独暴露为模型工具；不为增加调用次数而拆工具。

字段建议：`title` 非空；`due_at` 可空；`importance` 为现有 1–3；`estimated_minutes` 为现有 1–1440。建议值与原文明确值必须区分，含糊或冲突时间不得静默补全。原文依据也不能被当作新的系统指令。

计数由应用从有效草稿计算，不能直接采信模型声称的数量。示例：“识别到 3 项任务，其中 1 项可能重复”；用户丢弃后显示“保留 2 项待确认”。

## Schema v1：工具输入与输出草案

这里定义数据契约，尚未实现校验器或真实 Pi 调用，不修改当前 Task 数据模型。草稿比正式任务多出来源和缺失信息，不能直接当成数据库插入参数。

### 输入：模型提出的任务列表

| 字段 | 类型与约束 | 用途 |
| --- | --- | --- |
| `tasks` | 对象数组；可为空表示没有提取到任务 | 一次文本提取的结果；空数组不进入创建表单 |
| `title` | 去除首尾空白后非空字符串 | 简洁任务标题，可由原文概括 |
| `due_at` | 本地日期时间字符串 `YYYY-MM-DDTHH:MM:SS` 或 `null` | 原文明确时间的标准化结果；缺失或含糊时留空，不填写猜测值 |
| `importance` | 整数 1–3 | 明确等级或建议等级 |
| `estimated_minutes` | 整数 1–1440 | 明确时长或估计时长 |
| `field_sources` | 对象，包含上述四个字段的来源 | 界面标注和校验依据，不能代替人工事实确认 |
| `source_text` | 来自本次输入的非空原文片段 | 定位任务依据；多项任务可以共享同一段原文 |

来源枚举：标题为 `extracted/summarized`，截止时间为 `explicit/missing/ambiguous`，重要程度为 `explicit/suggested`，耗时为 `explicit/estimated`。`explicit` 表示原文明确给出；“明天下午五点”可结合固定参考时间标准化，但“明天下午”不能自行补成具体钟点。来源标注也是模型提议，需要应用校验和用户检查。

输入示例（虚构原文：“请提交周报；预约牙科检查。”）：

```json
{
  "tasks": [
    {
      "title": "提交周报",
      "due_at": null,
      "importance": 2,
      "estimated_minutes": 30,
      "field_sources": {
        "title": "extracted",
        "due_at": "missing",
        "importance": "suggested",
        "estimated_minutes": "estimated"
      },
      "source_text": "请提交周报"
    },
    {
      "title": "预约牙科检查",
      "due_at": null,
      "importance": 2,
      "estimated_minutes": 10,
      "field_sources": {
        "title": "extracted",
        "due_at": "missing",
        "importance": "suggested",
        "estimated_minutes": "estimated"
      },
      "source_text": "预约牙科检查"
    }
  ]
}
```

本地时间格式与现有任务表一致，不意味着已解决 T06 时区问题。参考时间由应用在请求开始时固定；跨天后不随重试重新解释“明天”。不同地区时间或日期含糊时要求补充。

### 输出：应用计算并生成

| 字段 | 约束与职责 |
| --- | --- |
| `schema_version` | 固定为 1；表示当前契约版本 |
| `status` | `prepared`、`validation_error` 或 `lookup_failed`；失败不呈现为没有重复 |
| `batch_id/revision` | 应用生成，标识当前草稿批次和修订，不接受模型自行指定 |
| `drafts[]` | 有效草稿，每项由应用分配 `draft_id`；不是正式任务 ID |
| `draft_count` | 应用按有效草稿实际计算，不能由模型指定 |
| `duplicate_check` | 成功时为 `complete`；没有匹配只能表述为“首版同名规则下未发现候选”，失败为 `failed/not_run` |
| `duplicate_candidates[]` | 含 `draft_id`、已有 `task_id`、标题、截止时间及 `same_title` 匹配原因；只读、仅未完成任务 |
| `within_batch_candidates[]` | 以草稿 ID 对表示同批同名提示，不计作已存在的数据库任务 |
| `needs_input[]` | 定位到 `draft_id`、字段、原因；不把缺失时间伪装成模型已经决定无截止时间 |
| `errors[]` | 包含输入位置、错误码和可展示消息；无效批次不静默丢掉其中的任务 |

批次号、任务计数、查重结果和用户确认状态属于应用的 Authority（权威状态），模型只能引用结果，不能自行提交这些字段或宣称用户已确认。工具参数拒绝契约外字段，包括 SQL、路径、保存指令和确认标记。

### 三层校验与流程门槛

1. **结构校验（Schema Validation）：** 类型、必填字段、枚举、数字范围；例如耗时必须为整数而不是“半小时”。
2. **业务校验（Business Validation）：** 日期必须真实有效；`due_at=null` 必须对应 `missing/ambiguous`，`explicit` 必须有有效时间；原文片段必须来自本次输入；查重失败不得生成可继续保存的成功状态。
3. **人工语义检查（Human Review）：** 是否漏任务、时间理解是否正确、估计是否合理。结构合法不能证明语义正确；原文片段存在也不能证明提取忠实。

建议首版任一任务有非法字段时返回定位错误，保留原文让模型修订，不静默接受部分任务而造成计数遗漏。缺失截止时间不算非法字段，可以先进入清单确认，但字段确认界面必须让用户补充或明确选择无截止时间；用户选择由界面记录，模型无权代选。

模型准备成功只表示草稿有效并完成查询，不表示已获用户确认，也不表示写库成功。用户修改后的来源由应用标为 `user`，不是模型输入允许的来源值。

权限边界的学习澄清：用户确认任务字段，不确认或执行模型生成的 SQL。模型无正式任务写权限，草稿工具仅读正式任务并管理内存草稿，界面记录当前批次/版本的用户操作，应用侧保存逻辑再次校验后使用参数化 SQL 写入。用户确认不使非法日期等无效数据变为合法；含糊时间应先提示补充，而不是把猜测时间伪装成确定事实等待人工兜底。

## 状态机与职责

```text
输入 → 分析中 → 工具准备草稿（校验 + 只读查重）
  → 待确认清单（数量、标题、候选重复）
  → 待检查字段 → 用户明确保存 → 已保存

识别有误 → 用户反馈 → 新版本草稿 → 重新确认
失败 → 保留输入、显示错误、允许手动录入
取消 → 结束本次运行并使草稿失效
```

- Harness 负责模型与工具循环；应用状态机负责确认界面和保存门槛，二者分开。
- 模型可以回复清单摘要，应用以工具实际输出渲染数量与按钮。模型不能通过一句“用户已确认”推动保存。
- 不向模型开放写库、任意 SQL、通用 shell 或任意文件读取工具。只读连接之外，运行环境也要防止绕过接口打开新的可写连接。
- 用户确认绑定当前 `batch_id/revision`。重新拆分任务后旧确认失效；取消后迟到结果不打开表单或保存任务。
- 用户修改标题或截止时间可能改变查重结果，保存前应重新检查相关修改并提示新增候选重复；该检查由应用触发。
- 真正保存沿用应用侧校验和写库逻辑，Agent 无正式任务写入权限；如何逐项或批量保存留待 T08 决定。
- Pi 在后台运行，持续读取 RPC 事件；接受 prompt 不等于执行完成，结束还须区分成功、失败和取消。无论分析结果如何，原有提醒 Workflow 独立运行。

## RPC 运行生命周期（离线控制已实现，真实Pi待验证）

官方依据：[RPC Mode](https://pi.dev/docs/latest/rpc)、[RPC Commands](https://pi.dev/docs/latest/rpc-commands)，2026-10-23 核对。接入实现须固定实际 Pi 版本并复核协议，不能将 latest 文档当作本机已安装版本的保证。

### 通信层与业务层分开

- Python 后台工作线程管理 Pi 子进程和持续读取；用 Qt 信号向主线程报告状态，不在 GUI 主线程等待网络或读取管道。
- RPC 命令和响应使用唯一 `id` 关联；stdout 按 LF 分隔 UTF-8 JSON 记录，stderr 单独处理，不能混入协议。读取必须连续，分段数据先缓冲到完整记录再解析。
- 会话事件通常没有命令 ID，因此单靠响应 ID 不足以识别每个分析结果。首版推荐一个 Pi 进程同一时刻只允许一个活跃分析，不排队多份分析。
- 应用生成本地 `run_id`，绑定进程代次、原文、参考时间和草稿版本；不要假设 Pi 会在所有事件中返回这个 ID。工具桥接必须继承当前应用上下文，不能采信模型自报的运行身份。
- 先安装事件监听、登记本次请求，再发送 prompt，允许快速事件早于命令响应到达；不能等收到响应后才开始监听。

### 状态及转换条件

| 应用状态 | 进入条件 | 用户看见什么 / 允许什么 |
| --- | --- | --- |
| `idle` | 没有活跃分析 | 输入、点击分析 |
| `starting` | 创建本地运行身份，后台启动与检查 Pi | 正在连接，可取消；启动失败保留原文 |
| `submitting` | 监听已就绪，发送带 ID 的 prompt | 正在提交，阻止重复点击 |
| `running` | prompt 被接受为 started，或已收到对应进程的开始事件 | 正在分析/检查候选重复，可取消 |
| `validating` | 运行已收敛，收集最终结果 | 校验当前草稿和查重状态，不立即打开确认表单 |
| `awaiting_list_confirmation` | 本次运行未失效，最终无失败/取消，有最新有效工具批次，查重成功 | 显示数量、标题和候选重复，等待确认 |
| `awaiting_field_confirmation` | 用户确认当前批次清单并处理候选重复 | 补充/编辑字段，尚未保存 |
| `saving` / `saved` | 当前版本经过用户确认，应用校验并执行写入；成功提交后才进入 saved | 保存中 / 保存成功，不以模型文字判定成功 |
| `cancelled/timed_out/failed` | 用户取消、应用截止时间到达、进程或最终结果失败 | 保留输入，原运行失效；重试须成为新运行 |

这些是 FocusPilot 应用状态，不是 Pi 原样提供的全部状态。零任务成功结果单独显示“未识别到待办”，允许补充文本，不进入空创建表单。

### 协议事件不能直接等同于业务成功

| 收到的消息 | 应用解释 |
| --- | --- |
| prompt 响应 success=true、disposition=started | 请求开始处理，不是分析成功 |
| disposition=queued | Pi 已排队；首版不主动使用排队，出现时按协议异常处理并取消清理，不能假装本次已开始 |
| disposition=handled | 输入被处理，没有为该 prompt 启动普通运行；不能无限等待 settled。首版普通分析若没有有效结果则报错，不能接受绕过草稿工具的回复 |
| 消息文本更新或单条消息结束 | 可更新进度；“完成了”等自然语言不能触发业务确认或保存 |
| 草稿工具调用成功 | 有待校验的中间批次；模型仍可能继续修订，暂不允许用户确认旧版本 |
| agent_end | 一次底层运行结束，仍可能继续重试或后续处理；不直接放行确认界面 |
| agent_settled | 自动处理收敛；检查最终错误/取消状态和工具批次后再决定业务结果，收敛本身不是成功 |

最终成功不能简单要求整段运行“从未报错”，因为可恢复错误可能已修复；应检查最终终态和最新批次。没有调用草稿工具、草稿无效或查重失败时，即使正常收敛，也不满足本功能成功条件。

### 取消、超时与迟到消息

1. 用户取消时立即使本地 run_id 和相关草稿确认失效，然后后台请求 Pi 停止；取消按钮不等待网络后才更新状态。
2. 协议支持先 clear_queue 再 abort，避免残留排队消息继续执行；具体命令按固定版本实现。停止响应不表示之前的工具没有执行，所以工具本身仍不得写正式任务。
3. 仍持续消费停止过程的输出，但失效运行的消息不更新当前表单、不恢复旧草稿、不写库。进程代次与运行身份都要检查。
4. 超时使用应用单调时钟设置绝对截止时间，不能每收到一个 token 就无限续期；自动重试也计入本轮总预算。具体时限与工具调用上限留待实现前确定。
5. 停止未在宽限时间内完成时，推荐结束应用自己启动的 Pi 子进程并重建，不操作其他进程；恢复前不复用旧事件流。具体宽限时间尚待确定。
6. 失败或超时保留原始输入，首版不由应用静默重新提交收费模型请求。用户明确重试创建新 run_id，旧确认和迟到消息不能复用；时间表达继续绑定原始参考时间，修改原文则新建参考上下文。
7. 取消不能承诺撤销已经发出的模型请求或已产生的费用。这里控制的是后续执行和本地结果使用，不回滚外部服务事实。

用户已明确期望取消后返回原始输入界面。推荐实现 `cancel_analysis` 确定性处理器：将取消视作 Control Signal，而不是发给模型的一条新业务请求；先撤销当前运行与草稿的使用资格，再恢复原文输入、显示“本次分析已取消”，后台继续停止与资源回收。清理尚未完成时可编辑原文，但显示停止状态并暂不复用该进程发起新分析。该规则针对分析/草稿阶段，不能类推为数据库已提交后仍能撤销保存。

推荐采用 **MCP Adapter（MCP适配层）**：Python应用通过现有RPC控制Pi，Pi通过本地stdio MCP服务调用Python只读业务工具，再由工具读取授权样例库。RPC与MCP是两条不同连接，不用将RPC工具事件改造成自定义执行命令。
